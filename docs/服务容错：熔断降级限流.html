服务容错：熔断 / 降级 / 限流

springcloud-demo 项目 · 归档日期 2026-09-20 · 学习路线「负载均衡 → 服务容错」的下一步 · 围绕三个核心概念、它们与项目真实代码的对应、以及选型 Sentinel 的完整说明

本项目的网关已经用 lb:// 走负载均衡、order 服务通过 Feign 调 service-system，链路已经跑通。负载均衡解决的是「正常时怎么走」，服务容错解决的是「坏了怎么办」。这是微服务在生产环境真正的难点，也是本项目代码里早已埋好的下一步方向——OrderServiceImpl.queryUserByFeign 里那句手写的 try-catch，正是熔断降级要自动化的东西。

一、三个概念：不是一回事，别混着说

它们在「请求进来 → 调下游 → 返回」这条链路上，各管一段。先看全景：

机制英文作用对象解决的问题
熔断Circuit Breaker下游服务下游挂了，快速失败，不傻等
降级Fallback业务结果失败后给一个兜底返回
限流Rate Limit入口流量流量太猛，超阈值直接拒绝

二、熔断（Circuit Breaker）—— 保护「下游」

它防的是什么：雪崩

设想 service-order 每次下单都要调 service-system 查用户。某天 system 挂了，每个请求都要等 3 秒超时才失败。流量一大，order 的线程全被这些「注定失败的等待」占满，最后 order 自己也被拖垮——这就是微服务里著名的「雪崩效应」：一个点故障，沿调用链传染，整片瘫痪。

熔断器像电路里的保险丝

它盯住对下游的调用，有三个状态：

  • 闭合（Closed，正常）：请求照常发出去。
  • 打开（Open，熔断）：失败率或慢调用比例超过阈值后，一段时间内不再真的发请求，直接快速失败——不浪费等待时间，也给了下游喘息机会。
  • 半开（Half-Open）：熔断时长过后，试探性放一个请求过去：成了 → 回到闭合；又失败 → 继续熔断。

一句话：熔断是「下游坏了，我不再傻等，快速失败」。 它保护的是调用方自己（避免被拖垮），同时也给了下游恢复的时间。

三、降级（Fallback）—— 保住「业务体验」

熔断打开后，请求被快速拒绝了，但用户还在等结果。降级就是兜底逻辑：系统坏了，给一个「说得过去」的返回，而不是干巴巴的异常。

对应到你的代码：现在 OrderServiceImpl.queryUserByFeign 里 catch 异常后抛一个 OrderException("调用用户服务失败，请稍后重试")——这其实就是最原始的手写降级。用 Sentinel 之后，可以把这个兜底抽成一个独立的 fallback 方法（比如「返回缓存里的用户信息」或「返回一个明确错误码」），框架在熔断/异常时自动调它。

一句话：降级是「坏了之后，给用户/调用方一个兜底结果」。 它和熔断常搭配出现，但概念不同——熔断决定「要不要发请求」，降级决定「不发/失败后返回什么」。

四、限流（Rate Limit）—— 挡住「入口」

前两个管「出去调用别人」，限流管「别人进来调我」。

比如你的下单接口一秒只能扛 500 个请求，突然来了 5000 个（秒杀/爬虫），服务会被打爆。限流规则会说：QPS 超过阈值，多出来的请求直接拒绝。

一句话：限流是「流量太猛，我按能力放行，超出的直接挡掉」。 它保护的是入口，对象是自己的资源。

五、三者的关系：为什么总被一起讲

它们都是「服务容错」这个母题下的手段，目标一致：让系统在部分组件出问题时，还能有尊严地活着，而不是整体雪崩。一个完整场景串起来：

秒杀高峰
   │
   ▼
① 限流 —— 挡住超出能力的请求（保护入口）
   │  少数放行
   ▼
② 调 service-system 时发现它已熔断
   │  快速失败，不等待
   ▼
③ 降级 —— 立即返回兜底结果
   │
   ▼
用户看到「稍后重试」，而不是页面卡死

六、选型：Sentinel

为什么是 Sentinel（而非 Resilience4j / Hystrix）：

  • 同源生态：Sentinel 是阿里巴巴开源的流量治理组件，属于 Spring Cloud Alibaba 生态，和本项目已经用的 Nacos 同源，接入最顺。
  • 可视化控制台 Dashboard：能实时看到每个接口的 QPS、熔断状态、被拒绝的请求数。亲手把 system 停掉，就能在面板上看到熔断器从「闭合」跳到「打开」——学习体感极强。
  • 规则动态生效：不用重启服务，在控制台改阈值秒级生效。

备选对照： Resilience4j 是 Spring Cloud 官方推荐、轻量纯 Java，但无自带可视化控制台；Hystrix 已停止维护，本项目的 Boot 4 + Cloud 2025 环境根本不会用。学习项目首选 Sentinel。

该覆盖的知识点（按顺序）

  1. 三个核心概念的区别（本文档已覆盖）。
  2. 流控规则：QPS 限流、线程数限流、关联/链路模式。
  3. 熔断降级规则：慢调用比例、异常比例、异常数。
  4. @SentinelResource + blockHandler + fallback。
  5. 整合 Feign：feign.sentinel.enabled=true，给 SysUserApi 配降级实现。

七、核心要点速记

  • 熔断（Circuit Breaker）：下游挂了快速失败，保护调用方自己，防雪崩。
  • 降级（Fallback）：失败后给兜底返回，保住业务体验。
  • 限流（Rate Limit）：流量超阈值直接拒绝，保护入口资源。
  • 三者目标一致：让系统在部分故障时「有尊严地活着」，而非整体雪崩。
  • 熔断决定「要不要发请求」，降级决定「失败后返回什么」——不是一回事。
  • 本项目已手写降级（queryUserByFeign 的 catch），接入 Sentinel 后改由框架自动化。
  • 选型：Sentinel（同源 Nacos + Dashboard 可视化 + 规则动态生效）。
