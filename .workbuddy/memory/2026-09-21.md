## 讲讲「Sentinel 规则下发」的底层机制（答疑，未改代码）

用户问「下发 QPS=2 规则这个动作怎么实现的」。做了源码级确认（读 m2 仓库里的 sources jar），把机制讲透并画了链路图：

- **8719 端口 = Sentinel 客户端内置的 HTTP Server**（`sentinel-transport-simple-http` 的 `SimpleHttpCommandCenter`），监听 `spring.cloud.sentinel.transport.port`。它不是野路子后门，而是 **Dashboard 与该服务通信的正规协议**——手工 curl 等价于「扮演一次 Dashboard」。
- 请求 → 按 URL 里的命令名分发 → `ModifyRulesCommandHandler`（源码注解 `@CommandMapping(name = "setRules", desc = "modify the rules, accept param: type={ruleType}&data={ruleJson}")`）→ 按 `type`（flow/degrade/...）解析 → `FlowRuleManager.loadRules(...)` 写进**内存**，立即生效、无需重启。
- **为什么 POST + JSON 会 415（源码铁证）**：`HttpEventTask.processPostRequest` 里明确 `throw new RequestException(StatusCode.UNSUPPORTED_MEDIA_TYPE, "Only form-encoded post request is supported")`——只收 form-encoded。GET 走另一条路 `processQueryString`，直接从 URL query 解析，不校验 Content-Type，所以 `GET /setRules?type=flow&data=<URL编码JSON>` 才是正确姿势。处理器里也是 `URLDecoder.decode(data, "utf-8")`，源码注释写着 `rule data in get parameter`。
- 规则生命周期：**存内存 → 服务重启即丢；Dashboard 重启规则也丢**（它也没持久化）。生产正解是规则存 Nacos + Sentinel DataSource 拉取（本项目已有 Nacos，天然可用）。
- 实测现象解释：**8719 端口是懒加载的**，服务刚启动不监听，要等第一次有请求经过受保护资源、Sentinel 完成初始化后才起来。

## 给后端加 CORS 配置（网关统一 + 服务侧开发开关）

用户要求「给后端加上 CORS」。过程中用真实 HTTP 请求实测出一个**必须做架构决策**的问题，最终按微服务惯例落地。

### 关键实测结论（`cors_verify.py`，7 项）

| 链路 | 结果 |
|---|---|
| 预检/实际请求 → 直连 :8083（两层都开了 CORS） | 1 个 ACAO，正常 |
| 预检 → 网关 :8080 | 1 个 ACAO，正常 |
| 无令牌 → 网关 :8080 | **401 且带 CORS 头**（浏览器能读到原因） |
| 携带令牌 → 网关 :8080 → 转发到 order | ❌ **2 个 `Access-Control-Allow-Origin`** → 浏览器拒绝 |

**根因**：请求经网关时，网关写一遍 CORS 头、转发回来的 service-order 又写一遍。**CORS 只能在输出链路的某一层写。**

### 落地方案（惯例：网关唯一出口）

- **网关**：新建 `gateway/config/CorsConfig.java`，注册 Servlet `CorsFilter`（`FilterRegistrationBean` + `HIGHEST_PRECEDENCE`，先于 `TokenAuthFilter`）。`allowedOriginPatterns("*")` + `allowCredentials(true)`（两者不能用 `allowedOrigins("*")`，会抛异常）。
- **service-order**：`config/CorsConfig.java` 保留但**默认关闭**，`@ConditionalOnProperty(name="app.cors.direct-enabled", havingValue="true")`；`application.yml` 里留了注释掉的开关说明。实测带 `--app.cors.direct-enabled=true` 启动后，直连 8083 恢复 1 个 ACAO。
- **压测工具** `tools/qps-tester.html`：默认目标改为网关 `:8080/api/order`，新增「访问令牌 + 自动登录」区块（调 `/api/auth/login`，默认 admin/admin123 换令牌），`start()` 时若令牌为空且目标是 :8080 就自动登录一次；`fire()` 带上 `Authorization: Bearer`。指向 8083 时不需要令牌。

## 修复压测中的 DuplicateKeyException（订单号唯一性，代码已改）

**现象**：压测时 service-order 报 `Duplicate entry 'SO20260921103646818' for key 'biz_order.uk_order_no'` → 500。

**根因确认（用户怀疑正确）**：`OrderServiceImpl.generateOrderNo()` 用 `SO + yyyyMMddHHmmss（只到秒）+ 3 位随机数`，同一秒只有 1000 个号码空间，按生日问题算：每秒 10 单就 4.4% 冲突、50 单 71%、100 单 99.4%、200 单 100%。**这不是运气问题，是概率上的必然**；反推每秒最多只能接约 4.5 单才低于 1% 冲突。日志里的 `SO20260921103646818` = `10:36:46` + `818`，时间戳确实只到秒。

**修法**：
- 新增 `service-order/.../support/OrderNoGenerator.java`（独立 Bean）：`SO + yyyyMMdd + IdWorker.getIdStr()`（MyBatis-Plus 内置雪花）= 29 字符（`order_no` 是 VARCHAR(40)）。日期只做人眼辨识，唯一性由雪花承担——职责分离。
- `OrderServiceImpl` 注入该 Bean，删掉 `generateOrderNo()`；写主表改走 `saveOrderWithUniqueNo(order)`：撞 `DuplicateKeyException` 就换号重试，最多 3 次，仍失败抛 503。**在同一个 `@Transactional` 内重试是安全的**（MySQL 重复键只回滚该语句；`save()` 是自调用、异常没穿过事务代理边界，不会被标 rollback-only），前面已扣的库存和订单在同一事务里一起提交。
- 同步更新了 `OrderDTO` / `OrderApi` 的 swagger example（`SO20260920153012001` → 新格式）。

**实测数据**（`.workbuddy/tmp/OrderNoStressTest.java`，报告 `order-no-report.txt`）：

| 场景 | 旧实现 | 新实现 |
|---|---|---|
| 每秒 100 单 × 5 秒 | 500 请求仅 387 唯一（113 个重复单号） | 500 全唯一 |
| 每秒 500 单 × 5 秒 | 2500 请求仅 917 唯一（1583 个重复） | 2500 全唯一 |
| 16 线程 × 10 万 | 160 万生成仅 1000 唯一 | 160 万全唯一 |
| 纯生成吞吐 | 854 万/秒（117 ns） | 26 万/秒（3783 ns） |

新实现慢的原因是雪花序列 `synchronized` 单锁、16 线程互抢；对本项目足够（真瓶颈是 MySQL insert），要更高就得换无锁实现或分 worker。

**多实例的坑（已写进 OrderNoGenerator 注释）**：MP 用「MAC + PID」哈希取低 16 位再模 32 推机器号，同机器上只有 32 个值，两个实例有约 1/32 概率撞同一机器号 → 雪花退化。生产上要 `IdWorker.initSequence(workerId, dataCenterId)` 显式指定。本项目单实例，暂无影响。

**踩到的工具坑**：`-pl <module>` 不带 `-am` 会因为 api 兄弟模块没 install 而依赖解析失败；`mvn -o` 离线也不行。编译日志必须 Grep 确认出现 `Compiling N source files`，看到 `Nothing to compile` 要警惕。

## 答疑：「显式分配 workerId」是什么意思（读源码纠正上一轮说法，未改运行逻辑）

上一轮（本文档第 91 行）说「生产上要 `IdWorker.initSequence(workerId, dataCenterId)` 显式指定」——**读 3.5.16 源码后发现这句不准确，已纠正**：

- `IdWorker.initSequence()` 设的是静态字段 `IDENTIFIER_GENERATOR`，而 `MybatisSqlSessionFactoryBuilder#build()` 里 **无条件调用 `IdWorker.setIdentifierGenerator(...)`** 覆盖它（`GlobalConfig.getIdentifierGenerator()` 非空时用配置的，为空时按 sequence 配置或网卡推导）。所以代码里 `@PostConstruct` 设的值会被覆盖，时序不可靠。
- **MP 3.5.7+ 原生支持配置**：`mybatis-plus.global-config.sequence.worker-id` / `.datacenter-id`（另有 `preferred-networks` / `ignored-interfaces`）。已从 `mybatis-plus-spring-boot-autoconfigure-3.5.16.jar` 的 `spring-configuration-metadata.json` 确认属性名就在 `global-config.sequence.*` 下。**这才是正解。**
- `Sequence` 常量：`workerIdBits = datacenterIdBits = 5` → 32×32=1024 节点，每节点每毫秒 4096 个号；`twepoch = 1288834974657L`（2010-11-04），41 位毫秒可用 ≈ 69.7 年。
- 自动推导的两个雷（源码 `Sequence`）：`getDatacenterId()` 取 MAC 最后两字节 → `>>6` → `%32`；`getMaxWorkerId()` 取 `hash(datacenterId + PID) & 0xffff` → `%32`，且 **`pid < 10` 时判定为容器环境并替换成随机数**；`MybatisSqlSessionFactoryBuilder:98` 在拿不到网卡时退回 `DefaultIdentifierGenerator.getFixedIdentifierGenerator()` = 固定 `(1,1)`。这两种情况所有实例都变同一节点。
- 哈希落位 vs 分配的概率：N 个实例至少一对同号 = 3.1%(2) / 9.2%(3) / 17.7%(4) / 28%(5) / 39.2%(6) / 61.4%(8) / 79.2%(10) / 98%(15) / 100%(20)。

已更新 `OrderNoGenerator` 的类注释（第 35-56 行），把 `initSequence` 说法换成 yaml 配置路径 + 覆盖陷阱说明，并列出上述两个雷。

## 答疑：真实项目怎么管 workerId（"启动时赋 WORKER_ID 是不是很容易重复/遗漏"）

用户问得很准。结论（已记入 MEMORY.md「编号管理选型」）：

- **判据**：唯一性只能来自「全局编排」或「原子申领」，不能来自"每个实例各自推导"。MP 默认的 MAC+PID 哈希、按 IP 取模都属于后者 → 只有概率保证。人工在启动命令里赋值属于「全局编排」，所以它是**对的**，只是**管起来累**（重复/遗漏是人的问题，不是机制的问题）。
- **Nacos 不能当发号器**：配置中心/注册中心提供的是「分发」（读一致），不是「分配」（原子申领）。把 workerId 放 Nacos 配置里，只是把人的责任从命令行搬到控制台。**"按 Nacos 实例列表顺序推编号"是个危险误区**：实例列表是最终一致视图，扩缩容期间两个实例可能在不同时刻算出同一序号并同时在跑 → 撞号。Nacos 的正当用途只有两个：存只读的编号台账；用实例 metadata 承载编排层已分配好的编号。
- **工业界的真实答案**：① 编排层分配（K8s StatefulSet ordinal / 部署清单环境变量）；② 集中式租约申领（美团 Leaf 用 ZooKeeper 顺序节点、百度 uid-generator 用 DB `WORKER_NODE` 表、滴滴 Tinyid 用 DB 号段）；③ 干脆用号段模式（`INCRBY` 一次 1000），把"编号管理"这个命题整个删掉。
- **租约方案的三条铁律**：抢必须是原子操作（Redis `SET NX EX` / MySQL 条件 `UPDATE` 且**检查影响行数=1**）；**续租失败必须让实例退出进程**（否则会带着已被回收的编号继续发号，这是最常被忽略的一点）；32 个编号抢不到要 **fail-fast**，不能悄悄退回默认 0。
- **两个具体坑**：Redis 若开 `maxmemory` + LRU 淘汰，租约 key 可能被淘汰 → 提前失约 → 撞号（必须 noeviction）；给 service-order 引入 Redis 还要新增 starter 并处理 `rxs` 主机名的 Lettuce DNS 坑（当前只有 auth/gateway 有 `RedisLettuceConfig`）。所以本项目再做租约版的话，**MySQL 条件 UPDATE 更划算**（零新增依赖）。
- 本轮未改代码，只在回答里给了 SQL 骨架（`snowflake_worker_lease` 表 + 条件 UPDATE 申领 + 心跳续租）与后续实现建议。

## Q&A：ZooKeeper 在当今微服务里的定位（未改代码）
- **结论**：ZK 已从"微服务标配"退化成"专用底座"——它只提供四个原语（临时节点 / 顺序节点 / Watch / 原子+强一致），注册中心、配置中心、分布式锁、选主这些"角色"都是别人拿原语拼出来的，所以能被 Nacos/Consul/etcd/K8s 逐层接走。
- **它唯一没有等价替代的能力**：**全局原子自增序号**（顺序节点）——这正是美团 Leaf 用它发 workerId 的原因；以及通用协调原语（Barrier、Leader 选举）。
- **被取代的三个真实原因**：① 运维+可用性代价（3/5 奇数节点、JVM/fsync 调优、长 GC 导致 session expired 误摘全部临时节点）；② CP 与服务发现的需求相悖（选主期间整集群不可写，秒级到几十秒服务发现直接不可用）；③ Watch 是一次性语义 + 万级实例的 watch 风暴会压垮 Leader。
- **本项目判定**：pom.xml 全量 Grep 无 `zookeeper/curator/dubbo/kafka` 依赖 → 不需要 ZK，Nacos 已覆盖注册+配置。只有将来引 Dubbo(ZK 注册中心) 或 HBase/老 Kafka 时才会"被动"用到，那时它是中间件的依赖而非架构决策。
- **顺手做的维护**：MEMORY.md 超过注入上限被截断，重新整理压缩（6966 → 约 6300 字符），合并重复表述、把"订单号"一节从踩坑叙事改为结论式，并把环境障碍细节统一指向 skill。

### Leaf 的事实核查（都是查过的，别再凭印象说）

| 事实 | 结论 |

### ★ 最值得抄的一处：Leaf 的取段实现（比"原子 SQL"更直白）

`IDAllocDaoImpl.updateMaxIdAndGetLeafAlloc`（已 fetch 源码确认）：

```java
SqlSession sqlSession = sqlSessionFactory.openSession();   // 无参 → autoCommit = false
sqlSession.update("...IDAllocMapper.updateMaxId", tag);
LeafAlloc result = sqlSession.selectOne("...IDAllocMapper.getLeafAlloc", tag);
sqlSession.commit();     // ★ 直到这里才释放行锁
```

update 与 select **同连接同事务**，UPDATE 持着 `leaf_alloc` 那行的 X 锁到 commit 才放，别人插不进来 → 读到的必然是自己刚写的值。**这比 `LAST_INSERT_ID(max_id + step)` 单语句方案更好**：后者依赖连接级 session 状态（连接池一换连接就拿到别人的值），Leaf 这个只靠行锁，语义直白。
（注：`getAllLeafAllocs` 用 `openSession(false)` 且不 commit，只读场景，靠 close 时回滚。）

### 三种落地形态，Leaf 只覆盖前两种

1. **Leaf 形态 A（嵌入式）**：业务 JVM 内嵌 `leaf-core`，**业务方自己持有号段库连接** → 本项目不想干这个。
2. **Leaf 形态 B（服务化）**：业务 → Leaf Server 单发 `getId` → 库。每次发号一次 RPC，把号段的吞吐优势让给了网络。
3. **号段下放（用户要的）**：业务本地双 buffer + 独立发号服务按段批发。**这一层 Leaf 不提供，省不掉。**

### 决策与理由

- **手搓**。理由不是"Leaf 质量差"（它的实现是对的），而是：① 用户要的形态 Leaf 本来就没有；② 引 Leaf 得先解决"不在中央仓库+三个 compile 依赖要排除"，成本高于照抄 ~500 行；③ 用户的目的就是搞懂号段模式，用 Leaf 恰好把最值得看的部分封装掉了。
- **选择 Leaf 的条件（本项目都不满足）**：在 Boot 2.x/3.x 上；要的就是"业务嵌入直连号段库"；只想有个能跑的分布式 ID 不关心机制；有私有 Nexus 能装 leaf-core。
- **该抄的三处**：`IDAllocDaoImpl`（取段事务写法）、`SegmentBuffer`（current/next + `AtomicBoolean threadRunning` 单飞 + `nextReady`）、`SegmentIDGenImpl.updateCache()`（剩余低于阈值时异步换段）。

### 顺手确认的两个判断

- **为什么用 MySQL 而不是 Redis `INCRBY` 领号段**：Redis 主从异步复制 + AOF everysec 都会丢最后一段，主库刚 `INCRBY` 完就挂、从库没追上 → **号段回退 → 重号**。号段的权威来源必须是"提交成功才算数"的存储，MySQL `UPDATE ... COMMIT` 满足，Redis 默认不满足（要 `WAIT`/RedLock 才够，那又慢回去了）。
- **预取要"单飞"**：只写 `if (remaining < threshold) prefetch()` 会让 2000 个并发线程一起打向 ID 服务（DDoS 自己），必须 `AtomicBoolean.compareAndSet(false,true)`；且**失败路径要复位标志并退避重试**，否则一次网络抖动就把预取永久锁死。
- **「段尽且 DB 不可用」必须 503，绝不降级为本地自增**（那就是重号）。和网关在 Redis 挂了时回 503 而非 401 是同一个判断逻辑。
- **号段 ID 连续即可枚举** → 若把对外订单号换成号段值会**加重** MEMORY.md 里挂着的 IDOR 待办（连猜都不用，`+1` 即可，还能靠号差反推单量）。号段适合做内部主键。

用户已确认：**先不动 service-order，ID 服务独立跑通**。本轮仅为选型分析，未写代码。
