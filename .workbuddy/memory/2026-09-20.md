- 【架构讨论·未动手】用户问「Redis Session 网关鉴权是不是在造轮子（对比 spring-boot-starter-security）」。结论：认证层**不算**造轮子——不透明令牌 + Redis 中心化会话是官方也支持的品类（等价 Spring Session Redis，区别只是令牌载体是 `Authorization: Bearer` 而非 Cookie SESSIONID）；SecurityContext 是 ThreadLocal，跨 JVM 不传播，Spring Security 本来就不提供「网关→下游」的身份传递，那一步必须自己设计。真正的缺口有两处（**待办**）：
  1. **授权层完全缺失**：现在只有「有没有登录」的二值判断，没有角色/权限/越权防护（张三能查李四的订单）。Spring Security 最值钱的就是这层，且必须在**每个下游服务**各做一遍（网关管不到方法级/数据级）。建议路线：认证保留自研，在 service-system/service-order 引入 `spring-boot-starter-security`，只用它做「PasswordEncoder(BCrypt) + 方法级 `@PreAuthorize` + 把网关透传的 `X-User-Id` 转成本服务 Authentication 放进 SecurityContext」，网关一行不用改。注意无状态 API 服务要关 CSRF、`sessionCreationPolicy=STATELESS`，否则登录接口会被 401/403。
  2. **密码明文比对**：`SysUserServiceImpl.verifyPassword` 第 85 行是 `Objects.equals(user.getPassword(), dto.getPassword())`，库里存明文。应换 `BCryptPasswordEncoder.matches()`（同时解决明文落库 + 非恒定时间比较的计时侧信道）。
  3. 附带风险：内网绕过网关直连 service-order:8083 时完全没有身份校验（下游无任何「头必须来自网关」的信任机制），这是微服务比单体多出来的攻击面。
